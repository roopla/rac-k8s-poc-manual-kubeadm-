How to use this guide

This guide rebuilds the whole lab by hand, from the Oracle Linux ISO to a 2-node Oracle RAC 19.32 database running in Kubernetes pods. Every step has the same four parts:

  • What: the action, in one line.
  • Why: what it is for, and what breaks without it. The reasons come from the Oracle doc and from what actually failed during the first build.
  • Commands: copy and paste as they are.
  • Check: what you should see before moving on.

Every block runs exactly as written. There's nothing to fill in or change: node names, addresses and disk IDs are either written out for each node or found by the block itself. Where a label says worker1, then worker2, paste the same block on each. Work through the guide in order, from 0.0 to the end; each step relies on the ones before it.

The automated scripts in rac-k8s-poc do the same work. Use them to rebuild quickly; use this guide to understand it.

Two traps cost time in the first build:

  • PowerShell is not bash. \", <<'EOF' and $VAR mean different things. Blocks marked PowerShell are written for PowerShell; long Linux scripts are sent to a node with a here-string piped into ssh ($x | ssh ... "tr -d '\r' | bash -s"), which avoids PowerShell's quoting entirely.
  • Git Bash needs ./ paths and winpty for programs that ask for a password (winpty python scan_test.py). .\file turns into .file there.

Architecture

Each RAC node is a Kubernetes pod pinned to its own worker VM. Each pod has three networks and two shared disks, and its Oracle software sits on its worker's own disk.

How to read it:

  • The public network (k8s-public) carries Kubernetes, Flannel's pod traffic and client connections. Each pod's eth0 is the RAC public network, and its node name, VIP and SCAN all resolve to that address through CoreDNS.
  • The two private networks (rac-priv1, rac-priv2) are the RAC interconnect. Multus gives each pod eth1 and eth2 on them, through macvlan on the workers' promiscuous NICs.
  • The ASM disks are attached to both worker VMs and handed to both pods as raw block devices. ASM builds the DATA disk group on them, which holds the database, the cluster registry and the voting files.
  • /u01 in each pod is a directory on its worker's /scratch disk. The Oracle homes and the node's local configuration live there and survive the pod being recreated.

Phase 0Windows host and VirtualBox networks

Result of this phase: an SSH key, an SSH configuration for the lab, and the VirtualBox networks every VM will use.

0.0 Start clean (only if this PC had the lab before)

What: removes everything an earlier build of this lab left behind: the four VMs (including the golden VM), their disks and the shared ASM disks, the k8s-public network, the SSH host keys remembered for the lab's ports, and the lab's lines in the Windows hosts file. On a PC that never had the lab, both blocks just report that there's nothing to remove.

Why: a rebuild trips over leftovers. VirtualBox refuses to create a VM, disk or network whose name already exists; old ASM disks still carry the previous cluster's ASM headers; and SSH refuses the new VMs' host keys on the same ports ("REMOTE HOST IDENTIFICATION HAS CHANGED").

Only the lab's own names are touched: ol98-golden, controlplane, worker1, worker2, the folder D:\VMs\rac-poc and the network k8s-public. Other VMs are left alone.

PowerShell
$VB = "C:\Program Files\Oracle\VirtualBox\VBoxManage.exe"; $Base = "D:\VMs\rac-poc"
$existing = (& $VB list vms) -join "`n"
foreach ($v in "worker1","worker2","controlplane","ol98-golden") {
  if ($existing -match ('"' + $v + '"')) { & $VB controlvm $v poweroff 2>$null; Start-Sleep 3; & $VB unregistervm $v --delete; "removed VM $v" }
}
$left = (& $VB list hdds) | Select-String '^Location:\s+(.*)$' | ForEach-Object { $_.Matches[0].Groups[1].Value } | Where-Object { $_ -like "$Base\*" }
foreach ($d in $left) { & $VB closemedium disk $d --delete; "removed disk $d" }
if (Test-Path $Base) { Remove-Item $Base -Recurse -Force; "removed folder $Base" }
if ((& $VB natnetwork list) -match 'k8s-public') { & $VB natnetwork stop --netname k8s-public; & $VB natnetwork remove --netname k8s-public; "removed network k8s-public" }
foreach ($f in "$env:USERPROFILE\.ssh\known_hosts", "$env:USERPROFILE\.ssh\known_hosts_rac_lab") {
  if (Test-Path $f) { foreach ($p in 2205, 2210, 2211, 2212) { ssh-keygen -R "[127.0.0.1]:$p" -f $f 2>$null | Out-Null } }
}
"--- left over (should list none of the lab VMs, and no k8s-public) ---"
& $VB list vms; & $VB natnetwork list

Then the hosts file, which needs PowerShell as Administrator. The first line shows what will be removed (nothing, on a PC that never had the lab); a backup is kept as hosts.bak.

PowerShell(Admin)
$h = "$env:windir\System32\drivers\etc\hosts"

0.1 Check the host

Why: two workers of 22 GB, a 4 GB control plane and Windows itself need about 56 GB of the 64 GB. Worker vCPUs come from the host's thread count: with 8 threads, workers get 4 vCPUs and each RAC pod 3 CPUs. Giving 6 vCPUs to each worker on an 8-thread host overcommitted the CPU in the first build.

PowerShell
Get-CimInstance Win32_Processor | Select-Object NumberOfCores, NumberOfLogicalProcessors
[Math]::Round((Get-CimInstance Win32_ComputerSystem).TotalPhysicalMemory / 1GB)
Get-PSDrive D | Select-Object Used, Free

Check: 8 or more logical processors, about 64 GB RAM, 250 GB or more free on D:. If you can, turn off Hyper-V, WSL2 and Memory Integrity so VirtualBox uses its own hypervisor; under Hyper-V it runs noticeably slower.

0.2 SSH key and lab SSH settings

Why: every VM gets this public key at install, so you log in without a password. All VMs are reached through 127.0.0.1 on different ports, and their host keys change when the golden image is sealed and cloned; the settings below stop SSH refusing those changes. They are for this lab only.

PowerShell
if (-not (Test-Path "$env:USERPROFILE\.ssh\id_ed25519")) { ssh-keygen -t ed25519 }   # press Enter at every prompt
$cfg = "$env:USERPROFILE\.ssh\config"
if (-not ((Test-Path $cfg) -and (Select-String -Path $cfg -Pattern '^Host 127\.0\.0\.1$' -Quiet))) {
@'

Host 127.0.0.1
    User root
    StrictHostKeyChecking no
    UserKnownHostsFile ~/.ssh/known_hosts_rac_lab
    LogLevel ERROR
    ServerAliveInterval 30
'@ | Add-Content -Encoding ascii $cfg
}
Get-Content "$env:USERPROFILE\.ssh\id_ed25519.pub"
Select-String -Path $cfg -Pattern '^Host 127\.0\.0\.1$' -Context 0,5

The key is only created if you don't have one yet, and the settings are only added once, so the block is safe to run again.

Check: one ssh-ed25519 ... line (your public key), then the Host 127.0.0.1 section with its five settings.

0.3 The VirtualBox networks

What: one NAT Network for the public side, SSH port forwards into it, and two internal networks for the RAC interconnect.

Why:

  • k8s-public (10.0.1.0/24): every VM on one network with internet access through NAT. Kubernetes, Flannel's pod traffic and later the RAC public network all run here. DHCP is off because every node gets a fixed address; Kubernetes and Grid both depend on addresses not changing.
  • Port forwards: the NAT Network can't be reached from Windows directly, so 127.0.0.1:2205/2210/2211/2212 are forwarded to SSH on each VM.
  • rac-priv1 and rac-priv2: two isolated internal networks for the RAC private interconnect (cache fusion and the cluster heartbeat). Two of them give Grid's HAIP redundancy. VirtualBox creates internal networks when a NIC is attached to them, so there is nothing to create here.
PowerShell
$VB = "C:\Program Files\Oracle\VirtualBox\VBoxManage.exe"
& $VB natnetwork add --netname k8s-public --network "10.0.1.0/24" --enable --dhcp off
& $VB natnetwork modify --netname k8s-public --port-forward-4 "ssh-golden:tcp:[]:2205:[10.0.1.5]:22"
& $VB natnetwork modify --netname k8s-public --port-forward-4 "ssh-cp:tcp:[]:2210:[10.0.1.10]:22"
& $VB natnetwork modify --netname k8s-public --port-forward-4 "ssh-w1:tcp:[]:2211:[10.0.1.11]:22"
& $VB natnetwork modify --netname k8s-public --port-forward-4 "ssh-w2:tcp:[]:2212:[10.0.1.12]:22"
& $VB natnetwork start --netname k8s-public
& $VB natnetwork list

Check: natnetwork list shows k8s-public, 10.0.1.0/24, DHCP disabled, and the four ssh-* rules.

Phase 1Golden VM and unattended Oracle Linux 9.8 install

Result of this phase: a VM called ol98-golden with a minimal Oracle Linux 9.8 install, reachable as ssh -p 2205 root@127.0.0.1.

Why a golden image: every node needs the same kernel, packages, kernel settings and container runtime. Preparing them once and cloning three times is faster and guarantees the nodes match; RAC and Kubernetes both misbehave when nodes differ.

1.1 Create the VM

Why each setting:

  • 2 vCPU, 4 GB, 50 GB disk: enough to install and prepare; each clone is resized later.
  • --paravirtprovider kvm: Oracle Linux's UEK kernel runs best with KVM paravirtualisation (stable clock, lower overhead).
  • NIC1 on k8s-public; NIC2 and NIC3 on rac-priv1 and rac-priv2 with promiscuous mode allow-all. RAC pods will put their own MAC addresses on these NICs through macvlan, and VirtualBox only delivers frames for unknown MACs in allow-all mode. Without it, the interconnect drops every packet.
  • Fixed SATA ports: port 0 for the OS disk, ports 1 and 2 later for the worker data disks, 3 and 4 for the shared ASM disks, 5 for the DVD.
PowerShell
$VB = "C:\Program Files\Oracle\VirtualBox\VBoxManage.exe"
$Base = "D:\VMs\rac-poc"; $Iso = "D:\ISO images\OracleLinux-R9-U8-x86_64-dvd-20260618.iso"; $g = "ol98-golden"
New-Item -ItemType Directory -Force -Path $Base | Out-Null
& $VB createvm --name $g --ostype Oracle_64 --basefolder $Base --register
& $VB modifyvm $g --cpus 2 --memory 4096 --vram 16 --graphicscontroller vmsvga --ioapic on --paravirtprovider kvm --rtcuseutc on --boot1 dvd --boot2 disk --boot3 none --boot4 none
& $VB modifyvm $g --nic1 natnetwork --nat-network1 k8s-public
& $VB modifyvm $g --nic2 intnet --intnet2 rac-priv1 --nicpromisc2 allow-all
& $VB modifyvm $g --nic3 intnet --intnet3 rac-priv2 --nicpromisc3 allow-all
& $VB storagectl $g --name SATA --add sata --controller IntelAhci --portcount 6 --hostiocache off
& $VB createmedium disk --filename "$Base\$g\$g-os.vdi" --size 51200 --variant Standard
& $VB storageattach $g --storagectl SATA --port 0 --device 0 --type hdd --medium "$Base\$g\$g-os.vdi"
& $VB storageattach $g --storagectl SATA --port 5 --device 0 --type dvddrive --medium $Iso

1.2 Kickstart and unattended install

What: a kickstart file answers every installer question, and VBoxManage unattended install boots the ISO with it.

Why these kickstart choices:

  • Static IP 10.0.1.5: the temporary address of the golden VM. Each clone starts on it and moves to its own address in Phase 4.
  • Your SSH key for root: passwordless access from the start.
  • SELinux enforcing, firewall off: the Oracle doc runs SELinux enforcing, with its own policy module for the RAC pods. The firewall is off to keep the lab simple (in production you would open the Kubernetes and Oracle ports instead).
  • One logical volume for /, no swap partition: Kubernetes requires swap off.

The password is typed at a prompt and only exists in a temporary file that is deleted straight after.

PowerShell
$VB = "C:\Program Files\Oracle\VirtualBox\VBoxManage.exe"; $Iso = "D:\ISO images\OracleLinux-R9-U8-x86_64-dvd-20260618.iso"; $g = "ol98-golden"
$sec = Read-Host "Root password for the lab VMs (8+ chars, no spaces or double quotes)" -AsSecureString
$pw  = [Runtime.InteropServices.Marshal]::PtrToStringAuto([Runtime.InteropServices.Marshal]::SecureStringToBSTR($sec))
$pub = (Get-Content "$env:USERPROFILE\.ssh\id_ed25519.pub" -Raw).Trim()
$ks = @"
text
cdrom
lang en_US.UTF-8
keyboard us
timezone America/New_York --utc
network --device=enp0s3 --bootproto=static --ip=10.0.1.5 --netmask=255.255.255.0 --gateway=10.0.1.1 --nameserver=8.8.8.8 --noipv6 --onboot=yes --activate
network --hostname=ol98-golden

sshkey --username=root "$pub"

firewall --disabled
firstboot --disabled

ignoredisk --only-use=sda

clearpart --all --initlabel --drives=sda

volgroup ol pv.01

%packages
@^minimal-environment
chrony

$ksFile = "$env:TEMP\ol98-golden-ks.cfg"
[IO.File]::WriteAllText($ksFile, $ks.Replace("`r`n", "`n"), (New-Object Text.UTF8Encoding $false))
& $VB unattended install $g "--iso=$Iso" "--script-template=$ksFile" --hostname=ol98-golden.localdomain --user=rac "--password=$pw" --time-zone=America/New_York --locale=en_US --country=US --start-vm=headless

Phase 2Golden VM OS prep for Kubernetes and RAC

Result of this phase: the golden VM has everything all three nodes share: the UEK R7 kernel, the kernel settings Oracle and Kubernetes need, the SELinux policy for RAC pods, and CRI-O with kubeadm, kubelet and kubectl. Run every block in a root shell on the golden VM:

PowerShell

2.1 Update the OS and pin the UEK R7 kernel

Why: the Oracle doc is tested on UEK R7 (5.15.0-208 or later). Oracle Linux 9.8 may default to UEK 8, so the newest UEK R7 kernel is installed and made the default. Running a kernel the doc wasn't tested on is a variable a PoC doesn't need.

golden VM
Connect firstssh -p 2205 root@127.0.0.1
dnf -y install dnf-plugins-core
dnf -y update
dnf config-manager --set-enabled ol9_UEKR7
dnf config-manager --set-disabled ol9_UEKR8 2>/dev/null || true
UEK7=$(dnf -q --disablerepo='*' --enablerepo=ol9_UEKR7 repoquery --latest-limit 1 --qf '%{version}-%{release}' kernel-uek | tail -1)
echo "UEK R7: $UEK7"
dnf -y install "kernel-uek-${UEK7}"
grubby --set-default "/boot/vmlinuz-${UEK7}.x86_64"

2.2 Kernel arguments

Why:

  • transparent_hugepage=madvise: Oracle recommends against THP always, which causes memory-access delays and, in RAC, node evictions. The doc asks for madvise on UEK R7.
  • clocksource=tsc: a stable clock in a VM. Grid's cluster time and its heartbeat timing are sensitive to clock jumps.
golden VM
Connect firstssh -p 2205 root@127.0.0.1
grubby --update-kernel=ALL --args="transparent_hugepage=madvise clocksource=tsc"

2.3 Swap off

Why: the kubelet refuses to run with swap on by default. Memory limits on pods only mean something when nothing is swapped out.

golden VM
Connect firstssh -p 2205 root@127.0.0.1
swapoff -a
sed -ri '/\sswap\s/ s/^([^#])/#\1/' /etc/fstab

2.4 Kernel modules and sysctls

Why:

  • overlay and br_netfilter, plus the three net.* settings: container image layers, and traffic between pods passing through iptables. Kubernetes networking needs them.
  • The Oracle settings: the doc's values for the worker hosts (fs.file-max, socket buffers, fs.aio-max-nr). These are host-wide settings that pods can't set themselves. The settings pods can set for themselves (kernel.shm*, kernel.sem) come later, in the pod definitions.
golden VM
Connect firstssh -p 2205 root@127.0.0.1
cat >/etc/modules-load.d/k8s.conf <<'EOF'
overlay
br_netfilter
EOF
modprobe overlay; modprobe br_netfilter
cat >/etc/sysctl.d/90-k8s.conf <<'EOF'
net.bridge.bridge-nf-call-iptables  = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward                 = 1
EOF
cat >/etc/sysctl.d/91-oracle-rac.conf <<'EOF'
fs.file-max = 6815744
net.core.rmem_default = 262144
net.core.rmem_max = 4194304
net.core.wmem_default = 262144
net.core.wmem_max = 1048576

EOF
sysctl --system >/dev/null

2.6 Tools and the RAC SELinux policy

Why:

  • Tools: podman builds the RAC image; unzip unpacks the Oracle software. It was missing in the first build, and the Grid unzip step failed until it was installed.
  • The rac-ocne policy module: RAC pods run systemd as PID 1 in the SELinux domain container_init_t. Oracle binaries on /u01 need to map and execute files, use text relocations and read the kernel log, which the default container policy forbids. This module is the doc's "Set up SELinux Module on Worker Nodes".
  • container_manage_cgroup: systemd inside a pod must manage its own cgroups. Without this boolean, the RAC container exited about one second after starting, with no log output. OCNE sets it through its own SELinux package; on kubeadm you set it yourself.
golden VM
Connect firstssh -p 2205 root@127.0.0.1
dnf -y install container-selinux selinux-policy-devel policycoreutils-python-utils podman tar rsync unzip jq iproute-tc bash-completion lsof
mkdir -p /var/opt && cd /var/opt
cat >rac-ocne.te <<'EOF'
module rac-ocne 1.0;

require {
        type container_init_t;
        type container_runtime_t;
        type container_file_t;
        type kernel_t;
        type bin_t;
        type lib_t;
        type textrel_shlib_t;
        class file { getattr map execute execmod setattr };
        class system syslog_read;
}

allow container_init_t container_runtime_t:file getattr;
allow container_init_t bin_t:file { map execute };
allow container_init_t container_file_t:file execmod;
allow container_init_t lib_t:file execmod;
allow container_init_t textrel_shlib_t:file setattr;
allow container_init_t kernel_t:system syslog_read;
EOF
make -f /usr/share/selinux/devel/Makefile rac-ocne.pp && semodule -i rac-ocne.pp
setsebool -P container_manage_cgroup on
cd ~

Check: semodule -l | grep rac-ocne prints rac-ocne, and getsebool container_manage_cgroup prints on.

2.7 Kubernetes and CRI-O packages

What: the Kubernetes v1.36 and CRI-O v1.36 repositories, then cri-o, kubelet, kubeadm, kubectl and cri-tools.

Why CRI-O: the doc builds the RAC image with podman and runs it as localhost/oracle/database-rac. CRI-O shares podman's image store, so a podman-built image is immediately visible to Kubernetes with no registry. With containerd you would have to import it separately. cri-tools gives crictl, which was also missing at first.

golden VM
Connect firstssh -p 2205 root@127.0.0.1
cat >/etc/yum.repos.d/kubernetes.repo <<'EOF'

baseurl=https://pkgs.k8s.io/core:/stable:/v1.36/rpm/
enabled=1
gpgcheck=1
gpgkey=https://pkgs.k8s.io/core:/stable:/v1.36/rpm/repodata/repomd.xml.key

EOF
cat >/etc/yum.repos.d/cri-o.repo <<'EOF'
[cri-o]
name=CRI-O
baseurl=https://download.opensuse.org/repositories/isv:/cri-o:/stable:/v1.36/rpm/

2.8 Configure CRI-O and pull the images

Why:

  • selinux = true: containers get SELinux labels, which the rac-ocne module is written for.
  • The pause image: set to the exact image kubeadm expects. Otherwise kubeadm warns about a mismatch, and two pause images get pulled.
  • No CRI-O sample bridge network: Flannel and Multus provide the pod networks.
  • Images pulled now: each clone then starts with the control-plane images already in place.
golden VM
Connect firstssh -p 2205 root@127.0.0.1
mkdir -p /etc/crio/crio.conf.d
printf '[crio.runtime]\nselinux = true\n' >/etc/crio/crio.conf.d/90-rac-poc.conf
PAUSE_IMG=$(kubeadm config images list 2>/dev/null | grep '/pause:' | head -1)
printf '[crio.image]\npause_image = "%s"\n' "$PAUSE_IMG" >/etc/crio/crio.conf.d/91-pause.conf
rm -f /etc/cni/net.d/*crio*bridge* 2>/dev/null || true
systemctl enable --now crio

3.3 The shared ASM disks

What: two 50 GB disks attached to both workers at once.

Why:

  • RAC is a shared-disk database. Both instances read and write the same data files, so both nodes need the same block devices. On real hardware that's a SAN; here it's VirtualBox shareable disks.
  • Fixed size: VirtualBox only allows the shareable type on fixed-size disks. Creating them takes a few minutes each.
  • Mode shareable: without it, VirtualBox refuses to attach the second VM, or worse, caches writes per VM.
  • One consequence: VirtualBox can't snapshot a VM with shareable disks attached, so don't snapshot the workers.
PowerShell
$VB = "C:\Program Files\Oracle\VirtualBox\VBoxManage.exe"; $Base = "D:\VMs\rac-poc"
New-Item -ItemType Directory -Force -Path "$Base\shared" | Out-Null
$port = 3
foreach ($d in "asm1","asm2") {
  & $VB createmedium disk --filename "$Base\shared\$d.vdi" --size 51200 --variant Fixed
  & $VB modifymedium disk "$Base\shared\$d.vdi" --type shareable
  foreach ($w in "worker1","worker2") { & $VB storageattach $w --storagectl SATA --port $port --device 0 --type hdd --medium "$Base\shared\$d.vdi" --mtype shareable }
  $port++
}
foreach ($d in "asm1","asm2") { & $VB showmediuminfo disk "$Base\shared\$d.vdi" }

Check: for each disk, showmediuminfo shows Type: shareable, and under "In use by VMs" both worker1 and worker2. Note the first 8 characters of its UUID: inside the workers the disk appears as /dev/disk/by-id/ata-VBOX_HARDDISK_VB<those 8>-....

4.1 What happens to each node, and why

Step controlplane worker1, worker2
a. Start and connect on 2205 yes yes
b. Name, identity, kubelet IP yes yes
c. Private NICs for Multus no: it has no NIC2/NIC3 yes
d, e. Data disks /var/lib/containers and /scratch no: it has only the OS disk yes
f. The doc's directories no yes (different on each worker)
g. HugePages no: 2048 pages would lock all of its 4 GB yes
Move to its own address, then check it yes yes

Why each step:

  • Name, identity and kubelet IP: the host name becomes the Kubernetes node name. New SSH host keys replace the ones the seal removed. --node-ip matters on the workers, which have three NICs: without it the kubelet may advertise the wrong address, and pod traffic between nodes breaks.
  • Private NICs with no IP: enp0s8 and enp0s9 are only "parents" for Multus macvlan interfaces. Each RAC pod gets its own interface, IP (10.0.11.x and 10.0.12.x) and MAC address on top of them.
  • Promiscuous mode (accept-all-mac-addresses yes): this was the cause of the hardest network failure in the first build, 100% packet loss between pods. VirtualBox's "Allow All" setting only takes effect when the guest NIC itself is promiscuous. Otherwise the virtual NIC silently drops frames addressed to the pods' macvlan MACs.
  • Data disks chosen by size, not by name: Linux disk names (sdb, sdc...) do not follow VirtualBox port order. On worker2 in the first build, /dev/sdc was a shared ASM disk, and formatting by name would have wiped the disk both nodes share. The ASM disks are 50 GB, so the sizes tell the disks apart. They're mounted by UUID for the same reason, and rsync -aAXH copies the images pulled in Phase 2 together with their SELinux labels.
  • The doc's directories with container_file_t: they're mounted into pods as hostPath volumes. With SELinux enforcing, a container can only use host files with the container file label. semanage fcontext makes the label permanent.
  • HugePages: the database SGA goes into 2 MB hugepages, which are locked, never swapped and cheaper for the CPU to map. Kubernetes only gives hugepages to pods on nodes that reserved them: the RAC pods ask for hugepages-2Mi: 4Gi, so each worker reserves 2048 pages. The doc reserves 16384 (32 GB); this lab scales it to the 22 GB workers.
  • Moving the address last, in the background: changing the public IP cuts the SSH session you're typing in. A first attempt died halfway through for exactly that reason. So the change runs detached from your session and ends with a reboot.
  • ssh-keygen -R before connecting: every clone has its own host key but answers on the same port, 2205. Without the 0.2 SSH settings, SSH refuses the new key with "REMOTE HOST IDENTIFICATION HAS CHANGED"; removing the old entry avoids that.

Phase 6Multus and the RAC private networks

Result of this phase: pods can have two extra interfaces, eth1 on 10.0.11.0/24 and eth2 on 10.0.12.0/24, with addresses you choose. A test between the workers proves the interconnect works before any Oracle software is involved.

6.1 Why RAC needs Multus

A Kubernetes pod normally has exactly one network interface, eth0, from the cluster network (Flannel here). RAC needs more than that:

  • A public network: client connections, the VIPs and SCAN. That's eth0.
  • A private interconnect: dedicated, low-latency and not routed through the cluster network. Cache Fusion moves database blocks between the instances over it, and the cluster heartbeat runs on it. If the heartbeat is lost, Grid evicts a node.

Multus is a "meta" CNI plugin that attaches additional networks to a pod. Each extra network is described by a NetworkAttachmentDefinition (NAD). This lab uses macvlan, which gives the pod its own MAC address directly on the worker's enp0s8 / enp0s9. Two networks give Grid's HAIP (highly available IP) two paths, so the interconnect survives losing one.

Phase 7ASM disks as Kubernetes block volumes

Result of this phase: the rac namespace, plus two PersistentVolumes and two PersistentVolumeClaims that hand the shared disks to the RAC pods as raw block devices.

7.1 Why block PVs, and why "by-id"

  • ASM wants raw disks. It manages the disks itself, with no filesystem. In Kubernetes that's a PersistentVolume with volumeMode: Block: the pod sees a device such as /dev/asm-disk1, not a mounted directory.
  • local PVs with node affinity for worker1 and worker2: the same physical disk is visible on both workers, so the PV may be used on either.
  • ReadWriteMany: both RAC pods use the same disks at the same time. ASM coordinates access between the instances.
  • persistentVolumeReclaimPolicy: Retain: deleting a claim never wipes the database disks.
  • /dev/disk/by-id/... instead of /dev/sdd: the doc uses /dev/sdd and /dev/sde, but sdX names can differ between the workers and change between boots (Phase 4). The by-id name comes from the disk's serial number, which is the same on both workers because it's the same VDI file. This is a delta from the doc.

7.2 Find the disk IDs (from the PC)

What: inside the workers, each shared disk appears as /dev/disk/by-id/ata-VBOX_HARDDISK_VB<first 8 characters of the VDI's UUID>-.... This block reads the two UUIDs from VirtualBox, finds the matching names on worker1 and worker2, and checks that both workers see the same two names.

Phase 8The RAC container image

Result of this phase: the image localhost/oracle/database-rac:19-ol9-slim is in the local image store on both workers. It's built from the doc's recipe and contains no Oracle software.

8.1 What's in the image, and what isn't

The image is a small Oracle Linux 9 system that behaves like a server:

  • systemd as PID 1: Grid Infrastructure is written for a full OS. It installs systemd services (oracle-ohasd), uses rc.local, and expects sshd. So the pod runs /usr/sbin/init rather than one application process.
  • oracle-database-preinstall-19c: creates the oracle user and the dba groups, and sets the limits and packages the database needs.
  • The ASM users and groups: grid (UID 54332) and asmadmin/asmdba/asmoper, with fixed IDs. The Oracle homes live on /u01 on the worker and survive the pod, so a recreated pod must have exactly the same UIDs, or every file would suddenly belong to a stranger.
  • setupContainerEnv.sh, run from rc.local at every start: gives /dev/asm-disk1 and /dev/asm-disk2 to grid:asmadmin with mode 660. Kubernetes creates block devices as root, and ASM must be able to open them. It also calls a restart hook on /u01 (Phase 14). That one line is this lab's addition.
  • Not in the image: the Grid and database software. They're installed into /u01, which is a host directory, so an image rebuild never touches an installed database.

The image differs from the doc's in these small ways:

  • the full registry name for the base image;
  • the dnf-makecache timer removed as well;
  • rc.local created if it's missing;
  • the NFS rpc_pipefs mount masked. It can't mount in a container and leaves systemd "degraded", which Grid's checks flag.

Oracle's GitHub RAC image was not used: its rc.local starts its own automation on every boot.

10.1 How each Kubernetes object maps to a RAC need

RAC needs Kubernetes object Why that object
Two servers with stable names StatefulSet per node (racnode1, racnode2) Gives a predictable pod name (racnode1-0) that becomes the host name Grid registers. A Deployment would give a random name on every restart.
Each node always on the same host nodeAffinity (worker1 / worker2) /u01 is a directory on that worker, and Grid's local registry lives in it. The pod can never move to another node.
Host names, VIPs and SCAN in DNS Headless Services (clusterIP: None) CoreDNS answers with the pod IP itself, not a load-balanced service IP. Grid needs real addresses that it can bring up and check.
Names that resolve before the pod is "Ready" publishNotReadyAddresses: true The pods are only Ready once port 1521 answers (after Grid). Grid's installer needs the names first, so without this, it would never be installed.
SCAN spread over both nodes Headless Service racnode-scan, selector cluster=racnode Matches both pods, so the SCAN name returns both IPs.
Private interconnect Multus annotation with fixed ips eth1 and eth2 at .141 and .142 on both private networks (Phase 6).
Shared ASM disks PVCs with volumeDevices Raw devices at /dev/asm-disk1 and /dev/asm-disk2, the same disks in both pods (Phase 7).
Oracle homes that outlive the pod hostPath volume on /u01 The software and the node's local configuration survive pod deletion.
Large shared memory emptyDir with medium: Memory on /dev/shm, plus hugepages-2Mi Default container /dev/shm is 64 MB. The SGA goes into hugepages.
Kernel IPC settings for Oracle Pod securityContext.sysctls kernel.shm* and kernel.sem per pod. They must be allowed in the kubelet config (Phase 5).
Grid managing IPs and priorities Capabilities NET_ADMIN, NET_RAW, SYS_NICE, SYS_RESOURCE... Grid brings VIPs up and down, runs real-time cluster processes and raises limits, without the pod being fully privileged.
Clean shutdown preStop: kill -SIGRTMIN+3 1 Tells systemd in the pod to shut down in an orderly way when the pod is deleted.
Passwordless SSH between nodes (installer) Secret ssh-key-secret, mounted read-only at /mnt/.ssh One key pair shared by both pods. The installers copy the software between nodes over SSH.
"Is this node usable?" readinessProbe on TCP 1521 Ready only when the listener is up. That's why the pods show 0/1 until Grid is installed.

11.1 Users, SSH keys, directories and profiles (both pods)

Why:

  • The installers SSH between the nodes as grid and oracle. Both users get the key pair from the Secret.
  • The directory tree is created empty and owned by grid (the Grid home and inventory) and oracle (the database base), as the doc does.

Phase 13Client connections inside and outside the cluster

Result of this phase: clients connect through the SCAN name and spread across both instances. That works from a pod in another namespace, and from Windows through NodePort services.

13.1 How a SCAN connection works here

  1. DNS lookup: the client resolves racnode-scan.rac.svc.cluster.local. The headless Service returns both pod IPs.
  2. SCAN listener: the client connects on port 1521 to one of the SCAN listeners (LISTENER_SCAN1 in racnode1-0, LISTENER_SCAN2 in racnode2-0).
  3. Redirect: the SCAN listener knows which instances offer the service and how busy they are. It sends the client to that instance's local listener, at the address the instance registered in local_listener.
  4. Session: the client reconnects there, and its session starts in ORCLPDB.

Step 3 is where Kubernetes setups break: the redirect address must be reachable by the client. Grid sets local_listener to the pod IP on port 1522, which any pod can reach.

Phase 14Surviving pod restarts

Result of this phase: a RAC pod that is deleted, crashes or loses its worker comes back by itself and rejoins the cluster, with the instance open. Clients carry on through the other instance in the meantime.

14.1 Why a restart breaks a RAC pod

When a pod is recreated (deleted, its container restarted, or its worker rebooted), Kubernetes builds a new container from the image. Only the volumes survive. /u01 is a volume, so the Grid home, the database home and the inventory are safe. But Grid's root scripts also wrote files into the container's own filesystem, and those are gone:

  • /etc/oracle/: ocr.loc and olr.loc (where the cluster registries are), scls_scr/<node>/ (the node's start state), and setasmgid;
  • the start-up machinery: /etc/init.d/init.ohasd, /etc/init.d/ohasd, and the oracle-ohasd systemd service with its enable links;
  • /etc/oratab, /etc/oraInst.loc, and /usr/local/bin/oraenv, coraenv and dbhome;
  • the grid and oracle home directories (SSH keys, known_hosts, .bashrc), and the pod's SSH host keys.

What it looks like: the new pod is Running but stays 0/1, and crsctl check crs says CRS-4047: No Oracle Clusterware components configured.

What happens in the meantime: node 1 evicts node 2, recovers its unfinished transactions, and carries on. Clients reconnect through SCAN to the surviving instance. No data is lost: the database is on the shared disks.

The pod usually gets a new IP (10.244.2.3, then .4, then .5 in the tests). Grid copes because it stores the VIPs as names (racnode2-0-vip, racnode2-0) and resolves them again through DNS each time a resource starts.

14.3 Automating it

The doc's own note recommends backing up the home directories and other root-filesystem content under /u01, so they can be restored. This lab does exactly that, and runs the doc's steps automatically at every pod start:

  1. snapshot.sh saves everything listed in 14.1 into /u01/app/restart-state/os-files.tgz, keeping owners, permissions and setuid bits. It refuses to overwrite a good snapshot with an incomplete one, and keeps the previous one as os-files.tgz.prev.
  2. The image's setupContainerEnv.sh already calls /u01/app/restart-state/onstart.sh if it exists (Phase 8).
  3. onstart.sh checks whether the oracle-ohasd service is missing, which means the pod was recreated. If so, in the background, it:
  4. restores the home directories, SSH host keys, oratab, oraInst.loc and oraenv;
  5. restarts sshd;
  6. runs tfa_setup;
  7. runs rootcrs.sh -updateosfiles, falling back to the snapshot's copy if that fails;
  8. runs crsctl start crs -wait;
  9. logs everything to /u01/app/restart-state/onstart.log.
racnode1-0, then racnode2-0
Connect firstssh -p 2210 root@127.0.0.1, then kubectl -n rac exec -it racnode1-0 -- bash; for racnode2-0: kubectl -n rac exec -it racnode2-0 -- bash

D=/u01/app/restart-state; cd /

       usr/local/bin/dbhome usr/local/bin/oraenv usr/local/bin/coraenv home/grid home/oracle)

paths+=( $(find etc/systemd -name 'oracle-ohasd*' 2>/dev/null) )

need=(etc/oracle/ocr.loc etc/oracle/olr.loc etc/oratab etc/oraInst.loc etc/init.d/init.ohasd
      etc/systemd/system/oracle-ohasd.service usr/local/bin/oraenv home/grid/.ssh/id_rsa home/oracle/.ssh/id_rsa)

EOF

  setsid nohup "$0" --run >> $log 2>&1 < /dev/null &
  exit 0

Demo Q&A

These are questions a Kubernetes or Oracle audience is likely to ask, with answers based on what this lab showed.

Kubernetes questions

Why StatefulSets and not a Deployment? A RAC node needs a stable host name, because Grid registers it in the cluster registry. A StatefulSet gives racnode1-0 every time; a Deployment would give a random name after every restart. There is one StatefulSet per node, so each can be pinned to its own worker.

Why is each pod pinned to one worker? Its /u01 (the Oracle homes and the node's local registry) is a directory on that worker. The pod can't move without its software and identity. RAC provides the availability, not Kubernetes rescheduling.

Why headless Services? Grid needs DNS names that resolve to the real pod addresses, for the node, the VIP and the SCAN. A normal ClusterIP service would hand out a virtual IP that Grid can't bring up or check. publishNotReadyAddresses makes the names resolve before the pods are Ready, which is when the installer needs them.

Why Multus? RAC needs a private interconnect separate from the client network. A pod normally has one interface; Multus adds eth1 and eth2 on dedicated networks. macvlan gives each pod its own MAC address on the worker's NICs, and two networks give Grid's HAIP redundancy.

Why raw block volumes? ASM manages disks itself, with no filesystem. volumeMode: Block hands the pod the device. The same disks go to both pods (ReadWriteMany), and ASM coordinates access between the instances.

Isn't it insecure? The pods aren't privileged, but they get extra capabilities (NET_ADMIN, SYS_NICE, SYS_RESOURCE and others), namespaced "unsafe" sysctls, and hostPath volumes. In production you would put them on dedicated, tainted nodes in a namespace with explicit pod-security exceptions.

What happens when a pod dies? Clients carry on through the other instance straight away. Kubernetes recreates the pod on the same worker in about 30 seconds. Without extra handling, Grid wouldn't start, because files outside /u01 are lost. This lab restores them and runs Oracle's restart steps automatically, and the node is back in about 4 minutes.

Oracle questions

Do the VIPs fail over? Not in the bare-metal sense. Each VIP is the pod's own IP, and Flannel routes a pod's address only to its worker, so it can't move. Clients survive a node loss through SCAN: the name resolves to the surviving node, and connect-time failover (plus FAN/ONS events) moves them.

The pod got a new IP after a restart. Doesn't that break Grid? No. Grid stores the VIP and SCAN VIP as names (USR_ORA_VIP=racnode2-0-vip) and resolves them through Kubernetes DNS each time it starts them. This was tested three times, with three different IPs.

Is it really patched to 19.32? Yes. opatch lspatches shows the RU in both homes. cdb_registry_sqlpatch shows the 19.32 RU and OJVM as SUCCESS in the root and the PDB. There are no unresolved PDB plug-in violations, which proves the seed is patched too.

What did the doc not cover?

  • DBCA memory: -memoryPercentage sizes from the worker's RAM unless patch 34436514 is applied, and that fix isn't in 19.32.
  • The restart steps don't recreate /etc/oratab, /etc/oraInst.loc or oraenv.
  • cluvfy needs plain (unhashed) known_hosts entries.
  • The Multus networks need "ips": true for fixed addresses.
  • On kubeadm, you set the SELinux boolean container_manage_cgroup yourself.

Is this supported for production? Oracle's certification matrix lists RAC 19c (19.28 and later) on Kubernetes on Oracle Linux 8 and 9. The only install guide it links is the OCNE one, and it doesn't say whether other Kubernetes distributions are covered. On kubeadm, get written confirmation from Oracle before running production. The build guide's "Production considerations" section lists what else would change.

Lab questions

Why VirtualBox and not Hyper-V? RAC needs disks shared by two VMs and promiscuous NICs for macvlan. VirtualBox has both: shareable fixed-size disks and Allow All mode. Hyper-V on Windows 10/11 can't share a virtual disk between VMs.

Why does the PC need a hosts file and port forwards? The lab is behind VirtualBox NAT. Port forwards reach the NodePorts, and the hosts file lets Windows resolve the VIP names that the SCAN listener redirects clients to.
